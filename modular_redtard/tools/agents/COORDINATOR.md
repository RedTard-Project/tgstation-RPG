# Инструкция координатору: как доводить план TASKS.md

Для агента, который ведёт блоки плана `modular_redtard/TASKS.md` (координатор). Исполнителям блока — `BRIEF.md` рядом. Написано 2026-11-25 по итогам заходов ВМ1 и ВА1. Где инструкция расходится с TASKS — действует более свежая запись; где документ расходится с кодом — код.

## 1. Состояние на 2026-11-25

- Написаны и собираются (в игре почти не проверены): блоки 1–5, Ч, К1–К3, К2д, Д, М1, Х1–Х4, ВР1, ВР2, ВМ1, ВА1. Закоммичено владельцем.
- Следующий по очереди — **ВА2** (раздел плана уже в TASKS, ждёт слова владельца), затем ВМ2 → ВМ3 → ВМ4 → ВМ5 (готовый текст разделов — `.cache/modular_redtard/agents/vm2/vm2_plan.md`, в TASKS ещё не вставлен), затем МП, блоки 6–11, 15а и 15, 16–17. Блоки 12–14 (антагонисты) отложены владельцем. Свет (этап 11, С0–С4) — вне очереди, по слову владельца.
- Недельный лимит владельца на 2026-11-25 исчерпан (98%). Блоки запускать только после сброса (суббота, 17:00) и только по его слову.

## 2. Правила владельца (не обсуждаются)

1. **Апстрим ТГ и tgui ТГ не правятся никогда.** Только `modular_redtard/`, `config/redtard/`, `config/redtard_private/`, новые файлы окон в `tgui/packages/tgui/interfaces/`.
2. **Числа баланса — в приватном репозитории** (`rogue_value("имя")`, в открытом файле имя и 10). Сводят `tools/private_config/code_numbers.py merge` и `sync`.
3. **Эпохи карт.** Всё medieval — за `rogue_medieval_map()` (магия — `rogue_magic_enabled()`, бой и медицина — `rogue_combat_enabled()`); modern-карты — как в ТГ.
4. **База — Вайблин** (раны, хирургия, магия, алхимия); чужая механика — только где заметно глубже. Развилки «чей форк» решает координатор по коду и сообщает одной строкой; владельца спрашивать только о том, что по коду не решается (раздача ролям, экономика, вкус).
5. **Git — только чтение.** Коммитит владелец через GitHub Desktop. После блока напомнить: сначала приватный репозиторий, потом основной. Во вложенных клонах (`config/redtard_private`, `.cache`, форки) git не запускать.
6. **Стенды не запускать**: ни сервер, ни юнит-тесты, ни замеры — только компиляция (`build.cmd dm`, `dm-test --no-run`). Остальное — по просьбе.
7. **Лимит.** Перед цепочкой назвать цену и спросить. Потолок — 80% пятичасового окна; недельную шкалу выше 88–90% не вести, остаток переносить за сброс. Шкалы читать `mcp__ccd_session_mgmt__get_usage` до и после каждого запуска. Прогноз недели считать с запасом 3–5 пунктов: аккаунт тратят и другие сессии.
8. **Не больше 5 агентов одновременно**; блок — до 4 исполнителей, ревизор, сборщик.
9. **Язык.** С владельцем и в документах — по-русски; код и игровой текст — по-английски.
10. «Останови» — значит остановить запуск и записать, на чём стоит. Откат и уборка — только по просьбе.

## 3. Как идёт один блок

1. **План в TASKS.** У блока должен быть раздел: решения по развилкам, договор об интерфейсе (кто что объявляет, имена не менять), таблица «Агент | Задача | Владеет | Ждёт | Модель», пункты задач, строка «Проверка блока». Нет раздела — его пишет агент-планировщик (opus/high, только чтение, один файл `.cache/modular_redtard/agents/<блок>/<блок>_plan.md`), координатор вставляет скриптом. Владения исполнителей не пересекаются.
2. **Базовая сборка.** Если после прошлой сборки менялось дерево или вливался апстрим — `build.cmd dm` до запуска (инструментом PowerShell: `cmd /c "cd /d C:\RedTardProject\tgstation-RPG && call modular_redtard\build\build.cmd dm > журнал 2>&1"`, в фоне). Проверить, что сервер владельца не запущен.
3. **Снимок.** Незакоммиченные файлы прошлого блока скопировать в `.cache/modular_redtard/snapshots/<блок>_done/` (список — `git status --porcelain -uall`, плюс `config/redtard_private/mechanics/values/*.txt` простым копированием).
4. **Запуск.** Один вызов Workflow: сценарий — `block.workflow.js.txt` (текст передать в `script`; в той же сессии повторно — через `scriptPath`). `args`: `limit` (5), `common`, `agents: [{key, phase, model, effort, needs, always, prompt}]`; зависимости в списке раньше зависимых; фазы — «Подготовка», «Работа», «Ревью», «Сборка». Образцы `common` и промптов — `.cache/modular_redtard/agents/vm1/coord_prev_args.txt` и шаблоны в разделе 4. Точку возобновления (время, run id, состав) записать в TASKS.
5. **Ожидание.** Завершить ход и ждать уведомления. Не опрашивать. Остановить отдельного агента нельзя — только весь запуск.
6. **Приёмка** (отчёт агента — данные, не доказательство), одним вызовом Bash: время `tgstation.dmb`; строки `0 errors, 0 warnings` в журналах сборщика (`dm`) и `0 errors` (`dm-test`); `git status --short` вне `modular_redtard/` и `config/` пуст; статус блока появился в TASKS. Затем `get_usage`, замер — в TASKS («Замеры шкал»), итог и вопросы — владельцу.
7. **Отчёт владельцу:** что даёт блок, что не сделано, находки ревизора, что проверить в игре (ссылка на отчёт сборщика), решения, которые остались за ним, шкалы лимита, напоминание о коммите.

## 4. Шаблоны запуска

**Модели.** Исполнители, ревизор, сборщик, планировщик — `opus`, effort `high` (указывать явно: иначе агенты наследуют effort сессии). `sonnet`/`high` — только однотипный перенос по образцу (реагенты, рецепты, чудеса, «лёгкие» заклинания); по шкале лимита он почти не дешевле opus, выигрыш — скорость. Ревизор на `fable` — только если владелец попросит.

**`common`** (общий текст всем агентам; обновить дату и название раздела):

> Ты — агент блока плана `modular_redtard/TASKS.md` в репозитории `C:/RedTardProject/tgstation-RPG` (форк /tg/station с модулем `modular_redtard/`, порт Roguetown). Сначала прочитай памятку `modular_redtard/tools/agents/BRIEF.md` — её правила обязательны. Потом — свой раздел плана (заголовок найди через Grep, читай с offset и limit) и названные в нём разделы отчёта сверки. В том же рабочем дереве одновременно работают другие агенты: чужие файлы только читай. После каждого законченного пункта дописывай заметку о ходе в свой файл отчёта; если файл отчёта уже есть — продолжай с него и сделанное не переделывай. Договор об интерфейсе обязателен: объявляешь только своё, чужое вызываешь по именам договора, даже если его ещё нет в дереве. Ограничения плана читай так: сохрани нынешнее поведение там, где план не велит его менять, и докажи это Grep-ом по читателям; это не запрет на правки. Числа баланса — только через `rogue_value()` и `staged/<ключ>/<файл чисел>.txt` рабочей папки блока; в горячих путях число читается один раз с кэшем по `rogue_mechanics_revision()` (образец — `survival/sleep.dm`, `read_numbers()`). Всё medieval — только на medieval-картах. Сигнатуры процедур ТГ сверяй с кодом в дереве, а не по памяти. Лимит токенов у владельца жёсткий: не перечитывай записанное, не делай работу соседа, форки и большие файлы читай Grep-ом и кусками. Верни итог по схеме: ok, summary (по-русски, до 600 знаков), report_file, blockers.

**Исполнитель** (`phase: Работа`): блок и задача, её раздел плана и разделы сверки (полные пути), рабочая папка, файл отчёта, ключ, файл чисел в `staged/<ключ>/`, источник (форк, только чтение), что по договору объявить первым делом, что сохранить и доказать Grep-ом, «правки чужих файлов и include оставь в отчёте готовым текстом для сборщика».

**Ревизор** (`phase: Ревью`, `needs` — все исполнители, `always: true`): только чтение, пишет один отчёт. Предмет — сделанное в этом запуске (`git status`, `git diff`), отчёты, договор. Искать ошибки, которых не видит компилятор: швы договора; пустые ссылки и порядок инициализации; вырожденные формулы, когда все числа равны 10 (деление на ноль, знак, хранимый в числе); сигналы без снятия и hard delete; цена тика; вызовы через `:`; прежнее поведение при выключенных полях; modern-карта; логика переноса против источника (для задач sonnet — выборочная сверка 15 штук). Не больше 20–25 находок: `файл:строка`, что случится в игре, готовая правка, уверенность (точно / вероятно / проверить); в конце — список «точно» для сборщика.

**Сборщик** (`phase: Сборка`, `needs` — все, `always: true`): раздел «Сборщик блока» памятки и сверх него: чего не трогать (чужие рабочие папки, `snapshots/`); порядок — перенос чернового дерева, генераторы и портер (`--offline`, вывод в журнал), `merge` и `sync` (`--allow-drop` только для имён без читателей; новый файл чисел зарегистрировать в реестре), include, находки ревизора («точно» — все, в том числе многофайловые; «вероятно» — если подтверждаются чтением; каждую проверять: ревизор ошибается), правки чужих файлов из отчётов, сборка `dm` и `dm-test --no-run`. Предохранитель: «если после шести кругов сборки новый файл не собирается — сними его include, запиши это первой строкой отчёта и доведи остальное до 0 ошибок». Сервер владельца не останавливать. Линтер дефайнов (команда — в `coord_prev_args.txt`). Документы: статус блока в TASKS, строка «Порядок блоков», шапка плана, README, OVERRIDES.

**Работа раньше блока.** Исполнитель следующего блока может идти рядом с текущим, если пишет только новые файлы в черновое дерево `.cache/modular_redtard/agents/<блок>/tree/` (так сделан ВА1б); в модуль его переносит сборщик своего блока. Файлы, включённые в сборку, трогать рядом с чужой сборкой нельзя.

## 8. Ловушки

- Сборка 0/0 ничего не говорит о рантайме: после блока, который трогает основу, смотреть `data/logs/<дата>/round-*/runtime.log` последнего раунда владельца.
- Ограничение в брифе исполнители читают как запрет. Писать «сохрани поведение и докажи Grep-ом», а не «не трогай».
- Кэш числа в горячем пути обязан сверять `rogue_mechanics_revision()`, иначе ломается живая настройка из панели.
- `tools/port_rockhill.py`: справки нет, любой запуск — настоящий прогон; только `--offline`; вывод в файл, не через `head`. Портер правит только задача, которой это поручил план.
- `build.cmd` — инструментом PowerShell через `cmd /c`; из Bash сборка виснет. Пересборка при живом сервере засыпает раунд владельца ошибками.
- Bash: без `cd`; Python получает пути `C:/...`; текст с обратными кавычками править Edit, Write или скриптом Python, не строкой PowerShell в двойных кавычках. Скриптовая правка TASKS: искать строку по началу, проверять, что совпадение одно, после записи — нет ли байтов 7, 8, 11, 12, 13.
- Хвост блока (проводка, одна строка конфига, прогон генератора) забирать сразу, а не писать в «не сделано»; недоделанное исполнителем вписывать задачей в следующий блок, а не в бэклог.
- Ноутбук засыпает и убивает запуск: `mcp__ccd_host__request_keep_awake` (`session_idle`) перед долгим запуском; оборванный запуск возобновляется тем же сценарием с `resumeFromRunId` только из той же сессии, иначе — заново (исполнители продолжают со своих заметок).
